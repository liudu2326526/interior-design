# 户型图纸解析（plan-import）

工作目录里有用户上传的户型资料：图片（JPG / PNG / WebP / 截图 / 扫描件）、PDF（多页时找含户型的那一页）、CAD 导出（DXF / DWG 转出的图片、打印稿或文本）、以及可能已经是 Plan 结构的 JSON、纯文字说明等，**格式不固定**。

你要**自行识别格式并直接读取**，不要要求用户转换格式、不要假设文件一定叫某个名字。识别户型后，输出一份 Plan JSON，写入当前工作目录的 `plan.json`。

## 1. 坐标与单位

- 全部长度单位是 **mm**。
- 2D 坐标系：x 向右，y **向下**；原点可自选，通常取户型左上角 `(0, 0)`。
- 墙、窗、门、推拉门都只能是**轴对齐矩形**（水平或垂直）。弧墙、斜墙用最接近的轴对齐矩形近似，并在说明里注明。

## 2. Plan 结构

```json
{
  "version": 1,
  "name": "方案名称",
  "bounds": { "x": -240, "y": -240, "w": 10240, "h": 8240 },
  "walls": [[0, -240, 8240, 0, "e"]],
  "wins": [[1000, 0, 2200, 240]],
  "doors": [{ "name": "入户门", "rect": [4580, 8310, 4820, 9200], "h": [4820, 9200], "c": [0, -1], "o": [1, 0], "len": 890, "entry": true }],
  "slides": [{ "rect": [10270, 7400, 10510, 9770], "v": true }],
  "rooms": [{ "id": "living", "name": "客厅", "poly": [[0, 0], [4000, 0], [4000, 3000], [0, 3000]], "mat": "tile800", "at": [2000, 1500] }],
  "materials": { "tile800": { "name": "800 地砖", "price": 220, "sw": "#ebe6dc" } }
}
```

### 字段说明

- `bounds`：2D 世界范围（含墙厚），四周可留 240mm 余量。
- `walls`：`[x0, y0, x1, y1, kind]`，坐标**已含墙厚**（矩形就是墙体本身，不是中心线）。`kind`：`e` 外墙、`b` 承重墙、`n` 非承重墙、`low` 矮墙。
- `wins`：窗洞矩形 `[x0, y0, x1, y1]`，贴在墙上，不要跨出墙体外。
- `doors`：平开门（门洞 + 门扇）。
  - `rect`：门洞矩形 `[x0, y0, x1, y1]`，落在墙体上。
  - `h`：**铰点坐标** `[x, y]`，取门洞矩形的一个角。
  - `c`：**关门时门扇的方向单位向量**，从铰点指向关门状态的门扇末端；必须沿门洞长边，取值 `[1,0]` `[-1,0]` `[0,1]` `[0,-1]`。
  - `o`：**开门方向单位向量**，从铰点指向开门状态的门扇末端；与 `c` 垂直，取值同上（`c·o = 0`）。
  - `len`：门扇长度（mm），等于门洞长边（例如 800–900）；`rect` 的短边只是墙厚（如 240），不要拿短边当 `len`。
  - 入户门加 `"entry": true`；一户型最多一个。
- `slides`：推拉门。`rect` 门洞矩形；`v` 为 `true` 表示门洞**竖向**（长边沿 y，门扇沿 y 方向推拉），`false` 表示横向。
- `rooms`：房间多边形。
  - `poly`：顶点数组 `[[x,y], ...]`，**至少 3 个点**，首尾**不重复**，不要自交；同一房间的顶点按**视觉顺时针**排列（y 向下时鞋带公式面积为正）。
  - `id`：英文小写、不重复；`name`：中文。
  - `mat`：`materials` 里的键；`at` 是标签位置，可省略（服务端取质心）。
  - 飘窗等不计面积的房间加 `"counted": false`。
  - **至少要有 1 个房间**，否则页面会拒绝加载。
- `materials`：键名尽量用固定 8 种：`wood`、`walnut`、`tile800`、`tile600`、`marble`、`antislip`、`terrazzo`、`carpet`；每项 `{ name, price, sw }`（`sw` 是色块 `#rrggbb`，`price` 是每平米单价，认不出就给合理默认）。

## 3. 识别规则

1. 优先使用图纸上标注的尺寸；没有标注时，用常见门宽 800–900 mm、600 地砖、墙厚等推算比例，并在说明里写清假设。
2. 墙厚默认：外墙 240 mm、内墙 120 mm、矮墙 100 mm。图纸有标注时以标注为准。
3. 房间 id 用英文小写（`living`、`master`、`kitchen`、`bath1`…），不要重复。
4. 房间名称用中文（客厅、主卧、厨房…）。
5. 门洞、窗洞要落在墙体上，矩形不要跨出墙体；门洞两侧的墙要断开。
6. 缺少的信息给**合理默认值**（门朝内开、房间地面用 `tile800`、无窗等），不要留空字段，也不要编造不存在的房间。
7. 材料无法判断时：卧室/客厅用 `wood`，厨卫/阳台用 `tile800` 或 `antislip`，并在说明里注明。
8. 若上传的 JSON 已经是 Plan 结构，按上面的规则**规整**后写出（补 `id` / `name` / `mat` / `at`、修正矩形顺序），不要原样照抄缺字段的版本。

## 4. 识别失败 / 不完整时的兜底

按以下顺序处理，不要硬编造：

1. **能认出户型轮廓和房间**：按图输出完整 Plan，用了哪些默认值 / 近似（弧墙、比例推算）写进说明。
2. **只能认出部分**（例如只有外墙轮廓、只有房间名、只有尺寸标注）：输出**最合理的完整 Plan**（至少 1 个房间，墙 / 地面给默认值），并在说明里逐条列出「哪些是推测」。
3. **是照片 / 效果图 / 无尺寸示意图**：按常见家具和门宽推算比例，注明「按常见尺寸推算，实际可能有偏差」。
4. **完全无法识别**（文件损坏、空白、与户型无关、图片看不清）：**不要写 `plan.json`**，在回复里说明原因和缺失信息，服务端会返回错误。
5. 多页 PDF：说明使用了第几页；其余页与户型无关就忽略。

## 5. 输出

1. 把完整 Plan JSON 写入当前工作目录的 **`plan.json`**（UTF-8，字段齐全，能被 `JSON.parse` 直接读取）。
2. 不要修改上传的原文件；不要在本目录创建 `plan.json` 以外的文件。
3. 回复用中文，不超过 300 字：识别到几室几厅、总面积、文件格式 / 页码、采用了哪些默认值或近似处理。

如果文件完全无法识别，按 §4 第 4 条处理：说明原因，不要写 `plan.json`。
